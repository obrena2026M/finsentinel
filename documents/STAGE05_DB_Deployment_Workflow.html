Overview

What this workflow supports

STAGE05 · DEP-07 · DEP-09…11 · DEP-14

Yes, a database deployment workflow can apply migrations and approved seed data to local or cloud-hosted databases, provided the application supports the target database engine.

FinSentinel currently uses SQLite. A SQLite file on suitable durable cloud storage is a different deployment profile from a managed PostgreSQL or MySQL service.

Choose a step to see its operator, checks and safeguards.

What happens today

The SQLite database is selected by DB_PATH and stored outside release folders by the current Windows deployment profile. At app startup, versioned schema migrations run and reference data is initialized. Demo-case fixtures are controlled separately.

Schema migrations

Versioned and automatic

runMigrations() applies ordered SQL files that are not yet recorded in schema_migrations. Each migration is transactional; an error aborts startup.

Reference data

Initialized at startup

seedReference() adds missing synthetic role users, the initial risk model, prompt versions and policy corpus data. It does not add demo cases.

Demo cases

Separate, explicit opt-in

SEED_ON_START=1 asks the server to create demo cases. The deploy script sets this off by default in production and enables seeding in a newly configured staging environment. Existing shared\.env values are not overwritten by later deploys.

SQLite recovery

File-based backup and restore

The release script takes a pre-deploy backup using the SQLite backup command and can restore that file on rollback. This mechanism is SQLite-specific.

Commands and implementation files

Local developer commands include npm run migrate and npm run seed; both use the configured DB_PATH. The latter creates synthetic demo cases and is not a generic production initialization command.

Implementation: src/db/connection.ts, src/db/seed.ts, src/server.ts, scripts/seed.ts, scripts/backup.ts, scripts/restore.ts, and scripts/deploy.ps1.

Known guard caveat: The CLI seed script currently checks whether ALLOW_SEED is non-empty. Therefore values such as 0 or false pass that check. Do not run npm run seed in production or wire it into a production workflow until the guard is hardened.

What “cloud database” means here

A cloud location does not automatically imply compatibility. Validate the storage/database engine and its operational guarantees before allowing writes.

Supported today

Local SQLite

Use the existing SQLite adapter and scripts with a persistent local file. Keep the database outside the immutable release directory.

Conditional

SQLite on cloud-hosted compute/storage

Potentially usable only if storage durability, SQLite locking/WAL behavior, single-writer access, backup and restore have been validated. Do not assume a network share is safe for SQLite.

Not supported today

Managed PostgreSQL, MySQL or another engine

A workflow alone cannot add compatibility. Do not point the current SQLite deployment at a non-SQLite service.

Required before enablement

Engine adapter and operational parity

Implement and test the driver, migrations, transactions, locking, full-text search, seeding, backup and restore for that engine before adding its workflow job.

Recommended workflow after another engine is supported

For multi-instance deployments, use one protected migration job with an exclusive migration lock. Keep schema changes, reference-data initialization and demo fixtures as distinct operations.

Demo-fixture decision

Local or staging + explicit opt-in: synthetic demo cases may be seeded. Otherwise: skip demo fixtures. Production demo-case seeding is not part of routine releases and must remain off by default (DEP-07, NFR-SEC-10).

Safety and recovery gates

Separate data classes

Migrations, reference data and demo fixtures have different purposes. Seeds must never overwrite operational cases, evidence, assessments, decisions or audit data.

Repeatable and reviewed

Use stable keys/version identifiers and safe rerun behavior. Keep migration and seed definitions in reviewed source control; never execute SQL supplied as workflow input.

Protect credentials and target

Store credentials in a protected secret store, scope them to the target, redact logs and assert environment plus database identity before writing. Do not accept arbitrary connection strings from workflow inputs.

Fail closed

Connection, permission, migration, seed or verification failures must fail the job and block promotion. Never silently skip a requested database change.

Account for schema rollback

Restoring application code does not necessarily reverse schema changes. Use backward-compatible expand/contract migrations or a tested restore/forward-fix plan.

Serialize writes

Prevent concurrent releases or app instances from applying the same migration or seed at once. Prefer a one-off migration job where runtime startup is not safe.
